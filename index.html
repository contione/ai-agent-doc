路线技术栈项目原则

先搞清楚：这些工具各自干什么

不要把框架当魔法。它们分别负责能力、流程和观测，组合起来才是业务 Agent 的工程底座。

能力组件

LangChain

连接模型、Prompt、结构化输出、工具、Retriever 和 RAG。适合快速搭积木。

流程编排

LangGraph

管理状态、分支、循环、重试、人工审批与长任务。适合做可控的业务工作流。

调试评估

LangSmith

追踪每次调用，查看 Prompt、工具参数、延迟和成本，并建立数据集做回归评估。

追踪链路、建立测试集、监控错误率与成本，用真实业务指标持续迭代。

推荐第一个实战项目

做一个“企业售后 Agent”，把知识问答和业务执行串起来。

用户：我想退掉订单 A123

用户请求 ↓ 意图识别 → 检查登录与权限 ↓ 查询订单 → 检索退款规则 ↓ 风险判断 ── 低风险 → 自动创建工单 └── 高风险 → 暂停并请求人工审批 ↓ 记录审计日志 → 返回带依据的结果
核心原则：查询可以自动化，退款、删数据、改合同等高风险写操作必须有明确权限和人工确认。模型不是保安，别让它拿着万能钥匙到处溜达。

业务 Agent 的 5 条底线

1. 先定义业务任务

从“自动处理退款”开始，不要从“做一个万能 Agent”开始。

2. 工具单一职责

明确的 API 胜过 execute_anything。边界越清楚，行为越可控。

3. 权限前置

权限过滤要发生在检索和执行阶段，不能只写在 Prompt 里。

4. 结果必须可追溯

RAG 要带引用，写操作要有审计日志，失败要返回真实状态。

5. 用数据持续评估

准备真实样例做回归测试，别用“我试了一次感觉还行”上线。

6. 先简单，再升级

能用确定性流程解决的地方，不要为了炫技强行塞一个 Agent。
