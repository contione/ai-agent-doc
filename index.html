先建立正确的全景图

业务 Agent 不是“让模型自由发挥”，而是把模型放进一个有边界的系统：模型负责理解和决策，工具负责执行，代码负责权限与规则，观测系统负责追责和改进。

用户请求→理解 / 规划→检索 / 调工具→规则校验→结果与审计
组件层

LangChain

模型、Prompt、结构化输出、Tools、Retriever、Embeddings 等通用组件的组合层。

适合：快速原型、RAG、单 Agent 工具调用。

流程层

LangGraph

用 State、Node、Edge 表达分支、循环、重试、人工审批和可恢复执行。

适合：复杂业务流程、长任务、多步骤 Agent。

质量层

LangSmith

追踪每一步输入输出、工具参数、延迟、Token 和错误；建立数据集做评估。

适合：调试、回归测试、线上监控与成本分析。

03

第 3-4 周：RAG，让答案有依据

学习文档加载、分块、Embedding、向量库、关键词检索、混合召回、Rerank、引用和拒答。重点是分开判断“召回对不对”和“回答对不对”。

文档解析→按章节切块→向量 + 关键词→重排序→带引用回答
业务底线：权限过滤必须发生在检索阶段；“请模型不要泄露”不是权限系统。文档版本、来源、页码和访问范围都要保存在 metadata。

作业：做一个公司制度问答，回答必须展示文档名和页码，找不到依据时明确拒答。

RAG 深入理解：别把向量库当魔法

RAG 的难点通常不在“接入一个 Chroma”，而在资料质量、切分策略、检索召回、权限隔离和评估。

阶段要解决的问题常见方案失败信号
解析PDF 表格、扫描件、标题层级按格式选择解析器，保留页码和章节文本顺序错乱、表格缺列
切分上下文是否完整优先按章节和段落，必要时再按长度答案条件与例外被拆散
召回能否找到相关内容向量 + BM25 + metadata filter同义问题搜不到、编号搜不准
生成是否忠实于证据引用、拒答、答案格式约束资料没说但模型自信补全
评估改动后是否退化黄金数据集、规则评估、人工抽检只测“看起来挺好”

何时用 Agent，何时不用？

YAGNI 也适用于 AI。流程确定、规则稳定的问题，用普通代码更便宜、更可控。

用确定性流程

固定字段提取、订单状态查询、明确条件的审批、报表计算、批量同步。

特点：输入输出稳定，规则可以写成代码或 SQL。

用单 Agent

用户表达不固定，需要在几个只读工具中选择，任务路径短且风险低。

特点：工具数量少，错误有兜底，单次任务可重试。

用 LangGraph

多步骤、有分支、有循环、要人工审批，或运行时间长且必须恢复。

特点：状态显式化，节点可测试，流程可审计。

判断口诀：能用规则解决就不用 Agent；必须理解自然语言才引入模型；必须管理状态才引入 Graph。

结课项目：企业售后 Agent

做完这个项目，你会把本页的大多数知识串起来，而不是只会背框架名。

业务需求

用户可以询问售后政策、查询订单、申请退款。系统必须识别意图、验证权限、检索最新政策，并对高风险操作人工审批。

用户请求→意图分类→权限检查→订单 / 知识库→风险路由→执行或审批

验收清单

能查订单且参数准确
答案显示来源与版本
无权限资料不可召回
退款失败不能谎称成功
高风险操作需要确认
每一步可在 Trace 查看
有 30 条回归测试样例
统计成本、延迟和失败率
不要做的事：不要给模型一个万能数据库工具；不要把所有文档混成一个无权限向量库；不要把 Prompt 当作安全边界；不要没有评估集就上线。
